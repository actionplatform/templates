| Env | Default | Serves |
|---|---|---|
| `GRPC_PORT` | `50051` | gRPC: `items.v1.ItemService`, `grpc.health.v1.Health`, server reflection |
| `PORT` | `8000` | HTTP `GET /health` — the platform sets it and probes it |

```bash
curl localhost:8000/health
grpcurl -plaintext localhost:50051 grpc.health.v1.Health/Check
grpcurl -plaintext -d '{"name": "pen"}' localhost:50051 items.v1.ItemService/CreateItem
grpcurl -plaintext localhost:50051 items.v1.ItemService/ListItems
```

### Why two ports

The platform's `web` contract is HTTP on `$PORT` with `GET /health`: the deploy probes and the cloud overlays assume it. gRPC needs HTTP/2 and its own health protocol, so the server answers both: `grpc.health.v1` on `GRPC_PORT` for gRPC clients and load balancers, and a plain `net/http` `/health` on `PORT` for the platform. Both read one `health.Server`: `/health` answers 503 as soon as the gRPC server starts draining.

## Proto

`proto/items/v1/items.proto` is the contract; the Go code in `internal/gen/` is generated from it and committed.

```bash
make generate      # buf generate, through docker
make lint-proto    # buf lint
```

Edit the `.proto`, run `make generate`, commit both.

## Layout

```
cmd/server/main.go        main only: env, listeners, app.New().Serve
proto/items/v1/           the .proto contract (buf.yaml, buf.gen.yaml at the root)
internal/
├── app/                  gRPC server, health service, HTTP /health, graceful shutdown
├── server/               gRPC handlers: request -> items rules, rule errors -> status codes
├── items/                business rules; never import gRPC
└── gen/                  generated by buf; do not edit
```

Request → handler (`server`) → rules (`items`). A handler holds no rules; the rules hold no gRPC. Add `repositories/` when a database or an external API appears, and interceptors in `app.New` when an RPC needs auth or logging.
